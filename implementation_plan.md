# WhatsApp Commerce Platform — Implementation Plan

Build the full agentic WhatsApp commerce platform: FastAPI backend with Gemini tool-calling agent, PostgreSQL database, Vite+React seller dashboard, deployable to Railway. All 6 architectural gaps from the review are addressed as first-class concerns, not afterthoughts.

## User Review Required

> [!IMPORTANT]
> **Deployment target**: Render (backend as Web Service, Postgres as managed DB, dashboard as Static Site). You'll need a Render account. The app will use environment variables for all secrets (Gemini key, WhatsApp credentials, JWT secret).

> [!IMPORTANT]
> **WhatsApp webhook URL**: Render gives you a public HTTPS URL automatically (e.g. `your-service.onrender.com`). After deploy, you'll configure this URL in the Meta Developer Dashboard as your webhook endpoint. During local dev, we'll use `ngrok` to tunnel.

> [!WARNING]
> **WhatsApp 24-hour window (Gap #4)**: The system will track `last_customer_message_at` per conversation. When responding after the window closes, it will automatically fall back to template messages. You'll need to pre-approve at minimum these templates in Meta's dashboard:
> - `order_update` — "Your order #{{1}} status: {{2}}"
> - `escalation_response` — "Hi {{1}}, regarding your inquiry — {{2}}"
> - `follow_up` — "Hi {{1}}, we have an update for you: {{2}}"

## Architecture Decisions — Fixing All 6 Gaps

### Gap #1: Stock Race Condition → Atomic Conditional Decrement
- `create_order` will use a single atomic SQL: `UPDATE products SET stock_quantity = stock_quantity - :qty WHERE id = :id AND stock_quantity >= :qty`
- Check `rowcount` — if 0, stock was insufficient (concurrent order got there first)
- No separate check-then-write. The database IS the lock.

### Gap #2: Idempotency → Conversation-scoped, not content-hashed
- Each `create_order` tool call gets a UUID generated by the Agent Engine before execution
- Stored as `idempotency_key` on the `orders` table with a unique constraint
- Keyed as `{conversation_id}:{pending_order_hash}` — so the same conversation can't create two identical orders, but a customer CAN reorder after cancellation (new conversation or cleared pending state)

### Gap #3: Escalation Resume → Explicit trigger path
- Dashboard POST `/api/escalations/{id}/resolve` with `{ mode: "instruct_agent" | "direct_reply", content: "..." }`
- **instruct_agent**: Writes a synthetic `seller_instruction` message to the conversation → calls `AgentEngine.resume_from_escalation(conversation_id, instruction)` → agent runs a new loop with the seller's instruction injected as a system-role addendum → sends result to customer
- **direct_reply**: Sends the seller's message directly via WhatsApp Cloud API → marks escalation resolved → logs as `sender=owner` message
- Both paths: unpause conversation, mark escalation resolved, push SSE update

### Gap #4: 24-Hour Session Window
- `conversations` table tracks `last_customer_message_at`
- Before sending any message, `whatsapp/client.py` checks: `now - last_customer_message_at > 24h`?
  - **Inside window**: Send normal text message
  - **Outside window**: Send template message instead, choosing the appropriate template
- Escalations approaching the window get a dashboard warning (SSE alert at 20h mark)
- Cron-like background check every hour for aging escalations

### Gap #5: Per-Conversation Locking
- PostgreSQL advisory lock using `pg_advisory_xact_lock(conversation_id_hash)` at the start of `process_message()`
- Second concurrent message for the same conversation blocks until the first completes
- Simple, no Redis needed, works with the existing Postgres connection

### Gap #6: Cost Tracking
- Every Gemini API call logs `prompt_tokens`, `completion_tokens`, `total_tokens` from the response metadata
- `agent_action_log` gets a `tokens_used` and `estimated_cost_inr` field
- Dashboard analytics shows cost-per-conversation and cost-per-order
